# User Story 11 backup and restore

Source-only handoff. Nothing in this increment has been compiled or run; no task
checkbox is changed and no platform acceptance is claimed.

## Delivered source

- `src/storage/migrations/0006_backups/up.sql` and the additive `backup_state`
  table in `src/storage/schema.rs`: first-user-data time, last successful
  automatic time and the persistent automatic-backup warning.
- `src/storage/backup/manifest.rs`: typed identity, category (manual, automatic,
  pre-restore, pre-update), platform, schema versions, catalog revision, payload
  size and SHA-256, dependency and portable-path metadata. Unencrypted local
  snapshots; no control directory, lease, activation record, destination-local
  profile identity, credential, dataset file or installer is ever read.
- `src/storage/backup/archive.rs`, `create.rs`: one fixed entry per archive
  (signature, bounded manifest, one SQLite payload). `VACUUM INTO` runs through
  Diesel after reading `library_state.revision` and is repeated up to three times
  if the revision moved, so a snapshot never mixes revisions. SQLite refuses
  `VACUUM` inside a transaction, so the read-transaction wording of T230 is
  satisfied by the before/after revision check instead. Free space is checked
  where the platform reports it (Unix); Windows reports unknown and relies on
  write errors, which remove partial files.
- `scheduler.rs`: first due 24 hours after initial user data, then 24 hours after
  the last successful automatic backup, one attempt per session, persistent
  warning cleared by a manual or automatic success.
- `retention.rs`: latest 30 automatic, all manual, latest five per safety
  category, recovery-protected archives never expire. The directory is the
  authority for listing; there is no separate history table to drift.
- `preview.rs`: signature, bounded manifest, exact payload length, checksum,
  unsupported or newer schema rejection, cross-platform, destination-location,
  dependency and pending-migration findings.
- `restore.rs`, `journal.rs`, `recovery.rs`: confirmed restore needs the exact
  previewed id and digest and a fresh pre-restore safety archive, stages and
  migrates a copy next to the live database, checks integrity, fsyncs, writes a
  journal (validated, then installing) and performs two same-volume renames.
  Recovery decides from the journal phase and which of live, aside and staged
  files exist: roll back before the swap, complete after it, refuse any
  contradictory state. The root lease is a borrowed proof for the whole call and
  only `library.sqlite3` is touched.
- `src/desktop/backup_commands.rs`: create, list, preview and restore handlers
  with save-all and unsaved-edit prerequisites and immutable preview handles.
- `src/presentation/settings/backup.rs`, `restore.rs`: status, warning, retry,
  folder and restore controls; play is never blocked by a backup warning.

## Tests authored

## Wiring

- `src/desktop/native/bootstrap.rs` runs `BackupRecovery::recover_blocking` on the
  executor before the document store opens, so a staged restore installs (or an
  interrupted one rolls back or completes) before any writer exists. It then
  creates `DesktopBackupService`, starts its scheduler and shuts it down before
  storage closes.
- A restore requested while the application runs cannot replace the open
  database. The bridge creates the pre-restore safety archive, stages and
  migrates a copy, writes a `pending` journal and asks the user to relaunch;
  recovery performs the two renames at the next start.
- `src/desktop/backup_bridge.rs` provides the typed operations (status, backup
  now, retry automatic, preview a listed archive, restore) and the service that
  runs them on the capacity executor. The coordinator routes
  `DesktopEnumCommand::Backup` to it and returns `DesktopEnumValue::Backup`.
- `src/presentation/app/backup.rs` mounts the backup and restore views in the
  Settings screen with the save-all and unsaved-edit prerequisites.
- The scheduler polls every 15 minutes, notes first user data, makes one
  automatic attempt per due period and never retries after a failure in the same
  session.

## Not done

- No compile, test, clippy or schema-check run.
- Archives can only be restored from the application backups folder; importing
  an arbitrary archive path needs a file-dialog purpose that does not exist yet.
- Restored game position and clock revision correlation is covered only by
  byte-level payload checks; no paused-game reopening test exists.
- Dependency and portable-path metadata is empty until US13 supplies references.
- Cross-platform and interrupted-rename behavior on Windows and a real power
  loss are unverified.
